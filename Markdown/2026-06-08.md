## ✅ PEAK CAN-FD 실드라이버 구현 (PeakCanDriver)
- 사용자가 **PCAN-USB Pro FD** (2채널) 연결 → PEAK 우선 개발 진행
- HAL `Peak/`:
  - `PeakInterop` — PCANBasic.dll P/Invoke (InitializeFD/Uninitialize/ReadFD/WriteFD/SetValue/GetErrorText, TPCANMsgFD)
  - `PeakBitrate` — (nominal,data) → FD 비트레이트 문자열 프리셋 (80MHz 기준, 500k/2M 등), 미지원 조합은 500k/2M 폴백
  - `PeakCanDriver : ICanDriver` — InitializeFD로 채널 open, PCAN_RECEIVE_EVENT + 백그라운드 스레드 수신, WriteFD 송신(QXMTFULL 재시도)
- `CanFdLength`에 DLC↔길이 변환 추가 (`LengthToDlc`/`DlcToLength`)
- `CanDriverConfig`에 `NativeChannelId`(PEAK 핸들/Vector 마스크), `FdBitrateString` 추가
- `CanConnection.CreateDriver`가 PEAK 선택 시 `PeakCanDriver` 사용, 스캔에서 받은 핸들 전달

## 🐞 버그 수정 — 실장비 송수신 시 HELLO_ACK 타임아웃
- 증상: PEAK 2대(송신/수신)로 전송 시 송신처는 ID로 송출하나 수신처 무응답 → HELLO_ACK 재시도 초과
- 원인: CAN ID 방향 불일치. 양쪽에 같은 TX/RX 기본값을 넣으면 수신처 RxCanId가 송신처 TxCanId와 달라 ISO-TP가 프레임을 필터링
- 수정:
  1. **역할 기반 ID 자동 배정** — UI 필드를 `S→R ID`/`R→S ID`(방향 기준)로 재정의, 수신처는 내부에서 TX/RX를 자동 스왑. 양쪽에 동일 ID 쌍만 넣으면 동작
  2. 연결 시 실제 적용된 TX/RX를 로그로 출력 (진단 용이)
  3. PEAK 수신 견고화 — 수신 이벤트 + **20ms 주기 폴링 안전망** (이벤트 미동작 환경 대비)
- 추가 확인: 사용자가 이전에 실행한 앱이 PEAK 상수 버그 수정 전 Release 빌드였음 → 재빌드로 해결(채널 스캔 정상화)

## ✅ 속도/처리량 최적화
- **CAN-FD 최대 속도**: 중재 1 Mbit/s + 데이터 8 Mbit/s (PEAK 1M/8M 프리셋 추가, 기본값 변경)
- **메시지 간 간격 축소**: CMAP ChunkSize 4 KB → **64 KB** (청크당 ISO-TP FC 왕복 16배 감소)
  - ISO-TP STmin=0, BlockSize=0(메시지당 FC 1회)는 이미 최적 상태 유지
- 효과: 1 MB 파일 기준 FC 왕복 256회 → 16회로 감소, 데이터 4배속(2M→8M)

## 🔎 처리량 분석 & TX 페이싱 버그 수정
- 증상: 8 Mbit/s 설정인데 실효 속도 ~499 KB/s (기대 ~900)
- 분석(물리적 한계): CAN-FD는 데이터 구간만 8M, 헤더(중재)+ACK/EOF는 1M 고정.
  - 64B 프레임 ≈ 헤더/트레일러 ~48bit@1M(~48µs) + 데이터 ~542bit@8M(~68µs) ≈ 116µs
  - → 29-bit ID 천장 ≈ **~550 KB/s**, 11-bit ID ≈ ~650 KB/s. 1 MB/s·900KB/s는 구조적으로 불가
- 소프트웨어 병목(주원인): `PeakCanDriver.SendFrameAsync`가 QXMTFULL 시 `Thread.Sleep(1)` →
  Windows 타이머 해상도(~1~15ms)로 8M 큐 재충전이 막혀 ~500 KB/s로 강제 제한
- 수정: QXMTFULL 대기를 **스핀(SpinWait/Yield) + 5s 타임아웃**으로 교체 → 큐 자리 나는 즉시 채워 버스 포화 유지
- 추가 개선 여지: 29-bit→11-bit ID 전환 시 헤더 오버헤드 감소(~15%)

## ✅ 표준 11-bit ID로 전환
- 기본 ID 체계를 29-bit 확장 → **11-bit 표준**으로 변경 (TX=0x101, RX=0x102, ExtendedId=false)
- UI에 **"확장 ID(29-bit)" 체크박스** 추가 (기본 해제 = 표준). 필요 시 다시 확장 가능
- ID 범위 검증 추가: 표준 ≤0x7FF, 확장 ≤0x1FFFFFFF
- 효과: 프레임 헤더 비트 ~18개 감소 → 처리량 약 +15% (천장 ~550→~650 KB/s)
- **실측 결과**: 499 → **596 KB/s** (TX 페이싱 개선 + 11-bit ID 합산, 11-bit 천장 ~650의 약 92%)

## ✅ Vector(VN1640A) 채널 열거 실HW 검증
- 사용자가 VN1600 시리즈(**VN1640A**) 연결
- vxlapi64.dll 동적 로드 정상, `xlGetDriverConfig` 파싱 검증
- 진단 도구 `dotnet run --project tools/HwProbe vectordump`로 원시 버퍼 분석:
  - channelCount=7, **실제 STRIDE=227**(추정 256 → 보정), name@0, mask@+42, **serial@+151** 모두 정확
- 보정 후 7채널 정상 스캔: VN1640A Ch1~5 (S/N 7114, mask 0x1~0x10) + Virtual Ch1~2 (S/N 7000)
- ⚠ 이전 "오프셋 HW 검증 필요" 경고 해소 — VN1640A에서 검증 완료
- 가상 채널(Virtual) 활용 시 물리 배선 없이 Vector 경로 루프백 테스트 가능

## ✅ VectorCanDriver 구현 + 가상채널 송수신 검증
- HAL `Vector/`:
  - `VectorNative` — vxlapi64.dll 동적 로더(EnsureRegistered, 어셈블리 DllImport 리졸버 1회 등록)
  - `VectorInterop` — CAN-FD P/Invoke + 구조체(XLcanFdConf/XLcanTxEvent/XLcanRxEvent, Pack=8) + 상수
  - `VectorCanDriver : ICanDriver` — xlOpenPort→xlCanFdSetConfiguration→xlActivateChannel, xlCanTransmitEx(스핀 페이싱), xlCanReceive(알림핸들+WaitForSingleObject 수신스레드)
- 채널은 채널 마스크(NativeChannelId)로 open, FD 타이밍 1M/8M (80MHz, abr 1+12+3, dbr 1+7+2)
- `CanConnection.CreateDriver`가 Vector 선택 시 VectorCanDriver 사용
- **검증(가상채널)**: `dotnet run --project tools/HwProbe vectortest` → 가상 Ch1(0x20)→Ch2(0x40) TX 5 = RX 5, 64B 데이터 일치 ✅
- 전체 Release 빌드/테스트 63개/앱 기동 정상
